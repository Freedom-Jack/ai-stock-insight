# Data and tool contracts

Status: normative application contracts, schema version `1.0` for the proposed implementation, refined in handoff Version 3.1 before implementation. These names are not vendor API payloads. Add fields through versioned migrations once data exists; keep external provider identifiers and schema versions separately.

## 1. Common conventions

All IDs are opaque strings. Application IDs are generated by the service; provider IDs retain their namespace. Resolve the owner/workspace from authentication, never from a model-supplied `owner_id`. Store UTC timestamps with explicit offsets and retain source timezone/precision. Use decimal representations for financial values; `null` means unknown, never zero. A percentage states whether it is a fraction or percentage points.

Every mutable business record has `created_at`, `updated_at` and a revision or immutable-version reference. Every committed record has `committed_at` and increasing `commit_seq`. Versioned evidence is append-only. Corrections link the prior version; they do not rewrite the past.

## 2. Core entities

| Record | Minimum fields beyond common conventions | Invariant |
|---|---|---|
| `Company` | name, identifiers such as CIK/provider keys, aliases | A company is not the same object as a listed instrument |
| `Instrument` | fields in [watchlist contract](WATCHLIST_SYNC.md), optional `company_id` | No merge by ticker alone; unresolved identities remain visible |
| `WatchlistSource`, `WatchlistSnapshot`, `SourceMembership`, `ThemeMembership` | Defined in watchlist contract; authority distinct from manual/file/API transport; nullable `external_list_id` | Only complete accepted snapshots reconcile source membership; no imported source is made native merely by storing it locally |
| `Theme` | name, research question, description, author, active state | A theme is not an inferred position or mandatory sector taxonomy |
| `Exposure` | from/to entity, relation type, valid interval, evidence IDs, uncertainty, status | A proposed relationship is distinguishable from supported exposure |
| `Goal` | objective, scope, output, schedule/version, timezone, start/report semantics, budget, autonomy, user attribution | Schedule changes create a new version; old obligations remain auditable |
| `ExpectedRun` | goal/version, occurrence key, coverage window, planned start, deadline, job IDs, timing outcome, coverage outcome | Exists independently of whether dispatch occurs |
| `Source` | provider/origin, family, route, expected cadence, retention/export policy, auth reference | Credentials are references to a secret store, never values |
| `DocumentVersion` | source key/URL, origin, version hash, content locator, publication/revision time and precision, received/captured times, parser version, entitlement | Exact input and its availability can be identified |
| `EvidencePassage` | document version, locator/span/table cells, allowed text, unit/heading context, extraction status | A passage resolves to the exact version, including qualifications |
| `Event` | kind, entities, scheduled interval/timezone, occurred interval, status, source and revisions | Future, tentative and unknown-date events are valid |
| `Claim` | proposition, subject/period, type, speaker, basis/units, evidence for/against, status, supersedes | User belief, issuer statement, verified fact and agent inference stay distinct |
| `ExpectationSnapshot` | company, metric, fiscal period, basis, units, value/range, definition/provider, provider-as-of precision, captured time, source/version | Guidance, Street consensus, model estimate and scenario assumption are different types |
| `ResearchCase` | question, scope, horizon, current interpretation revision, state, related events, reopening conditions | Evidence acquisition alone does not increment interpretation revision |
| `Hypothesis` | explanation or defined outcome, horizon, conditions, evidence, method, optional probability and resolution | A lucky anecdote is not adopted as a rule |
| `MethodVersion` | purpose, applicability, inputs, acceptable fallbacks, output contract, stop conditions, attribution | Every brief pins its actual method version |
| `BriefRevision` | conclusion, as-of, changes, claims, calculations, alternatives, gaps, next steps, dependencies, status | Corrections append; reviewed revision remains identifiable |
| `DecisionNote` | user text/attribution, thesis, horizon, intention/reported-action distinction, optional review conditions | The application does not infer that an order occurred |
| `Capability` | Contract in section 5 | Existence, permission and semantic fitness are separate |
| `CapabilityGap` | Contract in section 7 | Missing data is a durable limitation and possible build task |
| `Job`, `Run`, `ToolReceipt`, `Delivery` | Contracts below | Research, dispatch, delivery and user review are separate facts |

Use explicit relationship tables for claim dependencies, case evidence and brief-to-calculation links. Avoid storing the whole domain in an unqueryable JSON blob; JSON is appropriate for versioned provider payloads and method-specific fields.

## 3. Time, snapshots and replay

Track scheduled event time, actual event time, source publication/revision time, receipt/capture time and durable commit time independently. Preserve date-only/estimated intervals rather than inventing midnight precision. An event changing from tentative to confirmed creates an event revision.

Support two clearly named replay modes:

- `system_state`: only records committed at/before the requested commit boundary are visible. Their source publication times alone do not make them previously known to this system.
- `public_information_reconstruction`: documents may be acquired later if their public availability at the chosen cutoff can be supported. Label this reconstruction; do not claim Stock Insight observed them live.

Every run pins a base case revision and `base_context_manifest_id`. Subsequent reads append immutable version IDs to its read-set. At submission the service freezes a manifest, hashes it and records the method, model/executor version and calculations.

Jobs declare `information_policy.kind` as `live` or `fixed_cutoff`. A fixed policy requires `information_cutoff`; it applies to public availability, not later acquisition time. Historical/decision-time reconstruction uses this policy and excludes later information. Ordinary live work can include newly retrieved current evidence: preserve each input's timestamps, revisit any conclusions affected by new evidence, and freeze the final read-set and analysis `as_of` at submission. The displayed as-of is the analysis freeze time, not a claim that all inputs were observed simultaneously or have the same freshness. The pre-earnings expectation baseline remains independently immutable under either policy. Data arriving after final freeze belongs to a continuation.

An undated source can support general background but cannot establish a precise historical information boundary. Current revised data cannot replace historical estimates or macro vintages. A quote has an observation timestamp and feed-delay/session metadata, not just a capture timestamp.

## 4. Jobs, leases and results

`Job` fields: `id`, `case_id`, optional `expected_run_id`, trigger, objective, `expected_case_revision`, method suggestion, `information_policy` (kind and nullable cutoff), deadline, priority reasons, allowed actions, budget, state and idempotency key. `Run` fields: `id`, job, authenticated execution owner, lease hash/token reference, `fencing_generation`, expiry, executor/session IDs, actual model ID, reasoning effort when supported, effective executor configuration hash, authentication/billing mode, context/read-set IDs, usage, status and result hash. Never store credential values. Runtime model/effort comes from explicit application settings; it must not inherit the coding session's defaults silently.

Job states: `planned`, `ready`, `leased`, `accepted`, `partial`, `blocked`, `failed`, `superseded`. A retry after a terminated run creates a new run/generation. A blocked/partial result can schedule a new follow-up job; it does not mutate itself into a later answer.

Expected-run timing: `pending`, `on_time`, `late`, `missed`, `cancelled`. Coverage: `not_started`, `checked_no_change`, `checked_findings`, `partial`, `failed`. If late work recovers a missed run, preserve `deadline_missed_at` and a separate `recovered_by_job_id`; history must still count the miss. A schedule supersession cancels only future obsolete occurrences, not already missed ones.

### Claim and submission rules

1. `claim_research_job(job_id, execution_id, request_id)` is atomic. A retry by the same authenticated execution/request returns its existing lease. A competing execution receives busy/already-completed, never another execution's lease token.
2. Issue a new fencing generation on reassignment. A heartbeat extends only the current unexpired generation within the configured maximum run duration. Expiry/cancellation prevents future writes even if the host continues running.
3. `submit_research_result` authenticates scope, current lease/generation and base case revision. It freezes the read-set and validates the payload before one transactional commit.
4. An identical accepted submission returns the existing result ID. A different payload under the same completed submission key returns `idempotency_conflict`.
5. A competing committed interpretation produces `revision_conflict`. Retain a draft artifact for reconciliation; do not overwrite the newer case. Evidence gathered during the same run does not cause this conflict by itself.
6. A late artifact may be useful, but it cannot masquerade as an accepted timely result. A reconciliation job decides whether to incorporate it.

### Result payload

Required fields: `schema_version`, `job_id`, `run_id`, `lease_token`, `fencing_generation`, `expected_case_revision`, `status` (`complete`, `partial`, `blocked`), `as_of`, `method`, `conclusion`, `changes`, `claims`, `calculations`, `alternative_explanations`, `coverage`, `gaps`, `next_steps`, and `read_set_id`. The service returns `result_id`, accepted case revision, manifest ID/hash, commit time and sequence.

Claims contain type, text, evidence references and optional numeric metric/period/unit/basis fields. Calculations refer to persisted deterministic artifacts. Coverage refers to actual receipt IDs and required source families. Next steps contain a question/reason, trigger/deadline and whether they are research proposals or already permitted follow-up. A blocked result includes the precise blocking input and still preserves useful work.

Mechanical validation covers references, quoted spans, dates, unit compatibility, arithmetic references, allowed actions and ownership. A targeted semantic check assesses whether material claims are supported in context and whether contrary evidence was ignored. Another model's agreement is not independent factual confirmation. Validation errors identify specific fields/claims; do not repeatedly rerun the entire investigation for a repairable formatting problem.

## 5. Capability registry and invocation

A capability is a task-relevant operation implemented by an existing provider or local deterministic tool. Minimum fields:

| Group | Fields |
|---|---|
| Identity | `id`, semantic kind, provider/adapter ID, actual tool name, optional endpoint selector |
| Version | protocol version, provider schema hash, adapter version, documentation URL/checked date |
| Access | configured/authenticated state, entitlement evidence, company/interval/field restrictions, secret reference |
| Semantics | required inputs, provider input schema, units/basis/period meanings, known limitations, supported freshness/history |
| Operations | quota/rate policy, estimated/actual cost evidence, timeouts, retries, allowed network route, read/write classification |
| Evidence | last discovery, last successful receipt, validation/probe notes, current availability |
| Retention | permitted storage, excerpt, display/export and future redistribution policy |

Access observations are dimensions, not a single irreversible status ladder. Use documented, configured, authenticated, discovered, entitled, exercised and semantically validated evidence. An operation can be entitled but rate-limited, or successful but too stale for the current question.

`list_capabilities(question_kind, entity_ids)` returns compact available/limited capabilities and gaps. `get_capability(id)` returns the actual schema, requirements and restrictions. `call_capability(id, arguments, run_id)` validates against that pinned schema, checks authorization/budget, executes through the recording bridge and returns a receipt plus allowed data. The actual provider operation/endpoint is retained; the semantic kind does not obscure it.

Allowed dynamic discovery is `tools/list` on configured servers and reading public documentation. Runtime discovery does not authorize installing a server, opening new accounts, buying access or granting new scopes. Default vendor access is read-only even if a vendor MCP also exposes workspace/watchlist writes. Filter those methods out before exposing tools to the investigator.

Tool result envelope: `status`, `receipt_id`, `data`, `evidence_ids`, `freshness`, `coverage`, `warnings`, `retry_after`, `gap_id`. Status is one of `ok`, `partial`, `unavailable`, `not_entitled`, `rate_limited`, `invalid_input`, `unsupported`, `stale`, `error`. A valid empty search is `ok` with explicit search coverage; timeout or denied access is not an empty success. Apply field-level completeness when one payload contains both usable and absent fields.

## 6. Domain tool surface

All writes enforce authenticated scope and idempotency. Tool names below are implementation targets. Split a tool only when its authorization or response semantics materially differ.

| Tool | Inputs / output and authority |
|---|---|
| `create_research_request` | User question or attributed proposal → case/job and readable objective |
| `save_goal` | Goal version, recurrence and output intent → materialized obligations; user-authorized preference changes only |
| `claim_research_job` / `renew_research_lease` | Execution identity and request → scoped lease; current generation only |
| `get_case_context` | Case/revision/cutoff → bounded context, questions, method and dependencies |
| `search_evidence` / `get_evidence` | Entity/time/source/query or version locator → exact passages and provenance |
| `fetch_source_version` | Approved source identity/URL and run → retained version or typed gap; restricted destination policy |
| `list_capabilities` / `get_capability` / `call_capability` | Section 5 contracts; no arbitrary provider HTTP proxy |
| `compare_financials` | Compatible metric records and comparison definition → deterministic differences and rejected mismatches |
| `compute_price_context` | Instrument, interval, session, benchmark and price versions → returns/context with delay and adjustment basis |
| `run_historical_comparison` | Frozen cohort/trigger/outcome specification → sample, exclusions, statistics, sensitivity and limitations |
| `record_capability_gap` | Section 7 fields → deduplicated gap and engineering proposal |
| `propose_research_question` / `propose_method_revision` | Evidence, reason, applicability and trigger → attributed draft; no silent user-policy rewrite |
| `import_conversation` | User-selected supported export/messages → author-preserving records and candidate extractions |
| `submit_research_result` | Section 4 payload → accepted result or actionable conflict/validation response |
| `record_user_review` / `record_decision_note` | User attribution and named revision/text → reviewed state or journal note; never inferred agreement/trade |
| `get_research_record` / `export_research` | Record/version/filter → readable record or portable permitted export |

Watchlist import/configuration tools are application/UI operations; the investigator reads the normalized universe and proposes changes. It has no tool for arbitrary broker requests or automatic write-back.

## 7. Capability gaps as development inputs

`CapabilityGap` fields: `id`, `case_id`, `question`, semantic capability, required input/output semantics, `status`, attempted capabilities and receipt IDs, fallback used, analytical impact, reuse candidates with evidence, proposed remedy, access/cost/permission implications, acceptance example, priority reason and linked development-item ID.

Gap statuses: `not_connected`, `not_entitled`, `not_exposed`, `unsupported`, `history_missing`, `semantics_unverified`, `stale`, `rate_limited`, `temporarily_unavailable`. Track lifecycle separately: `open`, `investigating`, `planned`, `resolved`, `declined`. Recurring instances can link to one gap; a new provider entitlement does not resolve old research until the needed data is actually obtained.

Priority reflects recurrence, decision impact, likely reuse and remedy effort; it is not a fabricated return-on-investment score. The runtime may prepare a proposed coding task. It does not edit production code. A coding agent can implement the approved development scope in a branch/worktree, add a meaningful acceptance case and register the resulting version through normal release/configuration.

## 8. Receipts, provenance and coverage

`ToolReceipt` records tool/provider/schema version, run, sanitized argument hash and nonsecret parameters, requested interval, start/finish time, status, returned evidence/version IDs, source availability timestamps, freshness/delay, result completeness, quota/cost when known and actual trace class (`service_recorded`, `host_observed`, `model_reported`). Redact tokens and personal local paths before logs/exports.

Only service/qualifying host evidence can satisfy a required operational check. `model_reported` is an attribution, not proof. A retrieved result still needs relevance and interpretation review. Syndicated articles share an origin cluster; counting them as independent confirmation is invalid.

Coverage belongs to a named family and interval. Distinguish source content age from check age. A current successful check can find an unchanged old filing; a fresh cached summary cannot prove a failed source was checked today.

## 9. Delivery and recovery

Use separate `dispatch_outbox` and `notification_outbox` tables with stable deduplication keys, attempt records, next-attempt time and expiration. Both are committed with the state they announce. Consumers retry at least once; application-level keys yield one accepted effect.

Notification states: `queued`, `attempting`, `provider_accepted`, `confirmed_delivered`, `failed`, `expired`. User review is a separate record. The durable local inbox is committed with the brief; optional desktop/push delivery can fail without losing the brief. Do not label unsupported delivery confirmation as received/read.

On restart/resume: obtain the single-instance lock; reconcile missed obligations and leases; verify pending snapshot references; restore outbox processing; refresh stale sources; create one bounded catch-up per goal/coverage range; then normal dispatch. Preserve each missed occurrence. Supersede obsolete summaries without deleting their records.

## 10. Deterministic analysis contracts

Financial comparison declares its kind. `actual_vs_expectation` requires the same company and fiscal period with compatible metric definition, accounting basis, currency, share basis and duration. `period_trend` explicitly selects different periods for the same entity and checks comparable durations/definitions. `peer_comparison` explicitly selects different entities and aligns periods, currencies and metric definitions as appropriate; preserve genuine business/accounting differences instead of hiding them. Convert only with an explicit transformation and recorded inputs. Year-to-date cash flow is not a stand-alone quarter. Handle zero/near-zero expected values using absolute differences and a warning instead of an unstable surprise percentage.

Price context requires exact observation intervals, regular/extended session flags, benchmark alignment, corporate-action adjustment and currency. Daily bars cannot answer an intraday entry question. Missing prices exclude an observation with a recorded reason; do not silently keep only winners or survivors.

Historical comparisons require a declared observable trigger, universe available at the decision time, inclusion/exclusion rules, event-time alignment, outcome horizon, benchmark and code/data versions. Return all selected observations/exclusions, sample sizes, descriptive quantiles and sensitivity. Do not present a confidence interval or empirical probability without specifying the estimator and dependence assumptions. Predictive claims require prospective frozen forecasts and comparison with a baseline; historical replay alone cannot remove model-training hindsight.
